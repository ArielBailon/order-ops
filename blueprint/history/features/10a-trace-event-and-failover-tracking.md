# Feature: Trace event and failover tracking

**From build-plan:** feature 10a
**Build attempt:** 1
**Branch:** feature/trace-event-and-failover-tracking
**Status:** verified

## Goal

Every chat reply ends with one `trace` SSE event that summarizes the request: the trace id, route, tools, provider, failovers, tokens, cost and latency. The trace id is generated by the app before the request runs and is stored as `ChatTrace.id`, so later features can use the same id elsewhere (Langfuse in 10c, trace detail in 10b). A new persisted `failovers` count records how many times a model call failed and a different provider answered instead. The event carries metadata only, never message text.

## In scope

- **Trace id up front:** `TraceCollector` generates a UUID (`randomUUID`) when it is created; the stored `ChatTrace.id` is that id (today the database generates it at insert).
- **Failover count:** the collector counts a failover when a model call errored (`handleLLMError`) and the next call that completes is from a different provider than the one that errored. Persist the count as `ChatTrace.failovers` (`Int`, default 0) through a hand-written migration.
- **Totals:** a per-request summary computed once from the collector: provider of the last completed model call (null when none), token totals (input, output, cache read, cache write), cost as the sum of the priced calls, and the number of calls without a price.
- **`trace` event:** a new member of `ChatEvent` (service layer only, not an `AgentEvent`), sent once after `final` on a successful run and once after `error` on a failed run, formatted by the existing `formatSseEvent`. Its data equals the stored row: same id, route, tools, totals and latency. The record is built once per request and reused for both the event and the database write.
- **Docs:** the `AGENTS.md` Chat bullet lists the `trace` event and its fields.

## Out of scope

- Any read endpoint, the `viewer` role, eval results (10b); Langfuse and its dependency, keys and spans (10c); the console (11); rate limiting or budgets (12).
- Persisting per-request token or cost totals on `ChatTrace` (the existing `LlmCall` rows already hold them; the event totals are computed from the same calls), recording failed calls as rows, or storing the failover chain.
- Changing the failover model, provider order, pricing, prompts, routing or the eval harness. The eval runner consumes the graph's `AgentEvent` stream, not `ChatService.reply`, so it does not see `trace`.
- Sending `trace` after a client abort (nobody is reading) or while the stream is cut by shutdown: the row is still written as today.

## Data / contracts

- `ChatTrace.id`: the collector's `randomUUID()` v4 string, written explicitly; the column keeps `@default(uuid())`. Unique as before (primary key).
- `ChatTrace.failovers`: `INTEGER NOT NULL DEFAULT 0`, non-negative; existing rows read 0 (a historical trace that failed over is not recoverable).
- `trace` event (`event: trace`, `data:` JSON): `{ id: string, route: ChatRoute | null, tools: string[], provider: string | null, failovers: number, tokens: { input: number, output: number, cacheRead: number, cacheWrite: number }, costUsd: string | null, unpriced: number, latencyMs: number, status: 'ok' | 'error' }`. `costUsd` is the sum of the priced calls (six decimals, matching `Decimal(12,6)`), null when there are no priced calls. Metadata only: no message text, tool arguments or results.
- Order: `final` (or `error`) is always followed by exactly one `trace` on a stream that is still open; `approval_required` still precedes `final`. A client that stops reading at `final` simply never sees `trace`.
- Authorization: unchanged. The event goes only to the authenticated customer whose request it describes; the customer already sees the route and tool names. No new route.
- Failure semantics: the trace write stays best-effort and never changes the chat response; the event is built from the in-memory collector, so it is sent even if the database write later fails.

### 10a/F-15 [P3] closed - Restore failure note assumes the chain only stops at the restore line

**File:** docs/deploy.md:404
**Found:** 2026-10-20 by /audit independent current (scope: current; lens: quality)
**Why it matters:** The note says that if the chain stops "after the drop" the database is empty and to rerun only the restore line, never `up -d`. That is wrong for two other stops. (1) DROP fails (for example a prepared transaction or replication slot blocks `WITH (FORCE)`): the apps are stopped but the live database is intact, not empty; rerunning the restore line fails "already exists" and rolls back (no data loss), and the "repeat DROP" fallback fails again for the same reason. (2) `up -d` fails after a successful restore (build or health problem): the database is fully restored, and the note's advice (rerun the restore line, then DROP/CREATE and restore again) is needless and destructive; the right action is to fix the cause and rerun `$dc up -d`. `rm /tmp/restore.sql.gz` is also skipped, leaving a full customer dump in /tmp. The dump stays in S3, so nothing is lost beyond time.
**Suggested fix:** Replace the note with one line per stop point: stopped at `stop` or DROP (data intact, apps down: fix, rerun the block); stopped at the restore (database empty, rerun only the restore line); stopped at `up -d` (data restored, only fix and rerun `$dc up -d`, then `rm /tmp/restore.sql.gz`). Nothing is lost.
**Resolution:** The closing note in "Restore a backup" now has one bullet per stop point (stop/DROP: data intact, rerun the block; restore: database empty, rerun only the restore line; up -d: data restored, rerun only `$dc up -d` then rm the dump). Docs only; the destructive block is unchanged (same md5).
**Re-review 2026-10-22:** The restore section now has one bullet per stop point with the right database state and next action; the destructive block is unchanged. See F-21 for one edge the bullets do not cover. Closed.

### 10a/F-21 [P3] invalid - Restore note says a DROP-stage stop leaves the database intact, but CREATE can fail after DROP

**File:** docs/deploy.md:553
**Found:** 2026-10-22 by /audit (scope: path; lens: quality; builder session, not an independent review)
**Why it matters:** The first bullet says that if the chain stops at `stop` or `DROP` the live database is intact and the whole block can be rerun. The `psql` call runs `DROP DATABASE` and `CREATE DATABASE` as two separate `-c` commands. If `DROP` succeeds and `CREATE` then fails (for example the server runs out of disk), the database no longer exists, and rerunning the whole block fails at `DROP` ("does not exist") every time. Unlikely, and nothing is lost beyond time (the dump is in S3), but the note is wrong for that case. Not run: psql's exit status with a failing second `-c` was not checked.
**Suggested fix:** Add one clause to the first bullet: if `DROP` succeeded but `CREATE` failed, the database is gone; fix the cause, run only `CREATE DATABASE orderops;` and then the restore line. Nothing is lost.
**Resolution:** Marked invalid on the owner's explicit decision (2026-10-22) after observing psql in a throwaway postgres:16-alpine container (no network, no volumes, removed afterwards). psql with two -c arguments and no ON_ERROR_STOP runs both and exits with the status of the last. Case C: DROP succeeded and CREATE failed left the database gone and exited 1, as the finding said. But case D: rerunning the real block against the missing database made DROP error ("does not exist"), CREATE succeed and psql exit 0, so the chain continued to the restore. The finding's consequence (rerun fails at DROP every time) is wrong and the existing advice to run the whole block again works. Only the phrase "the live database is intact" is imprecise for case C; left as is by the owner's choice. No docs change.
